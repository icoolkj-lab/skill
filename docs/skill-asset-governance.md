# Skill Asset Governance

## Purpose

Manage collected assets as a searchable, auditable library that can be safely reused. Collection alone does not imply quality, compatibility, permission to redistribute, or permission for commercial use.

## Asset types

- **skill**: one callable capability with a Skill entrypoint.
- **skill-suite**: coordinated collection of skills, with a suite entrypoint and child records.
- **tool**: executable utility or application that may support Skills.
- **project**: complete application or engineering repository, not necessarily a Skill.
- **template**: reusable starting files.
- **dataset**: structured data used by an asset.
- **reference**: documentation or knowledge material.
- **other**: only when none of the above fit; explain in notes.

## Intake workflow

1. Record source repository / URL and collection date.
2. Preserve upstream license files, copyright notices, and relevant provenance.
3. Store unreviewed assets under `incoming/` or mark the catalog lifecycle `incoming`.
4. Triage asset type, duplicates, suite/child relationships, scope, and destination.
5. Review quality, security, dependency, licensing, and portability.
6. Verify by static inspection or runtime test. Record test environment and evidence.
7. Publish into `skills/<category>/...` only after required checks are met.
8. Archive superseded versions with a reason; do not silently overwrite provenance.

## Review checklist

### Identity and structure
- [ ] Unique stable ID; descriptive name and trigger/use description.
- [ ] Correct asset type; suite and child relationships recorded.
- [ ] Exactly one canonical entrypoint or a clearly documented suite entrypoint.
- [ ] Directory names are predictable; no unnecessary nesting.
- [ ] No temporary/cache artifacts, accidental secrets, or unexplained binaries.
- [ ] References, scripts, assets, and examples are actually used and paths resolve.

### Skill instructions
- [ ] Frontmatter parses and includes `name` and `description`.
- [ ] Description says what it does and when it should be invoked.
- [ ] Instructions are actionable, concise, and not contradictory.
- [ ] Referenced files are linked using correct relative paths.
- [ ] Tool/platform prerequisites and limitations are documented.
- [ ] Examples are relevant and not stale.

### Security and supply chain
- [ ] Inspect scripts and executable files before use.
- [ ] Identify network calls, shell commands, file writes, credential handling, and data exfiltration risks.
- [ ] Do not commit tokens, credentials, private user data, or secrets.
- [ ] Record upstream source and version/commit where available.
- [ ] Check license and copyright; unknown is not a permission grant.

### License / reuse
- [ ] License evidence path or source link recorded.
- [ ] Commercial use, redistribution, and modification permissions recorded separately.
- [ ] Unknown or restrictive license: keep status blocked/pending; do not promote as freely reusable.
- [ ] Preserve notices and required attribution.

### Verification
- [ ] Static check passed or findings documented.
- [ ] Runtime test performed where feasible.
- [ ] Required dependencies and environment identified.
- [ ] Installation and invocation tested, or status clearly marked untested.

## Grades

- **A**: strong instructions, clean structure, dependencies and source/license clear, verified in a documented environment.
- **B**: useful and basically sound, minor fixes/documentation needed; usable with caveats.
- **C**: incomplete, unverified, unclear provenance/license, or substantial cleanup required; hold for review.
- **D**: duplicate, obsolete, unsafe, broken, or low-value; archive/reject only after evidence and decision.

Grade is a quality signal, not a legal permission signal. License status is tracked separately.

## Lifecycle values

`incoming → triage → reviewed → verified → published → archived`

A status may move to `rejected` when the asset is not suitable. Keep a record of why; don't erase provenance.

## Catalog rules

- Stable IDs should use lowercase kebab-case and should not be derived solely from display names when collision is possible.
- `path` is the canonical repository path.
- Category is one primary category; cross-domain use belongs in tags.
- Do not fabricate author, source, version, license, test results, or compatibility.
- Record child skills separately when they can be invoked independently.
- Registry should be machine-readable and validated against `catalog/schema/skill-record.schema.json`.
- Derived counts, category totals, and reports should be generated by scripts rather than manually edited.

## Safe cleanup

Delete only after confirming exact duplicate content, no unique dependencies/references, and a canonical copy. For binaries or large assets, confirm the skill's runtime/build requirements. Prefer moving rejected/superseded assets to an archive with provenance over irreversible deletion until repository history and downstream references are checked.
